1. This process of precomputing and updating the results of a query is called **materialization**

2. The elapsed time from the moment when a user makes a request until they receive the requested answer is called Response time.

3. The number of requests per second, or the data volume per second, that the system is processing is called **Throughput**

4.  **Retry storm**
	- if a long queue of requests is waiting to be handled, response times may increase so much that clients time out and resend their requests. This causes the rate of requests to increase even further, making the problem worse—a _retry storm_.
	- Even when the load is reduced again, such a system may remain in an overloaded state until it is rebooted or otherwise reset. This phenomenon is called a **_metastable failure_**, and it can cause serious outages in production systems

5. To avoid retries overloading a service,
	1. **Exponential backoff** - increase and randomize the time between successive retries on the client side
	2. **Circuit breaker** - Temporarily stop sending requests to a service that has returned errors or timed out recently
	3. **Load Shedding** - The server can also detect when it is approaching overload and start proactively rejecting requests
	4. **BAck Pressure** - send back responses asking clients to slow down

6. As a server can process only a small number of things in parallel (limited, for example, by its number of CPU cores), it takes only a small number of slow requests to hold up the processing of subsequent requests—an effect known as **_head-of-line blocking_**.

7. **Beware that averaging percentiles is mathematically meaningless**. The right way of aggregating response time data is to add the histograms

8. **Fault & Failure**
	1. **Fault** - A fault occurs when a particular _part_ of a system stops working correctly
	2. **Failure** - A failure occurs when the system _as a whole_ stops providing the required service to the user

9. **_Single Point Of Failure_ (SPOF)**
	1. If a system cannot tolerate a certain part becoming faulty, we call that part a _single point of failure_ (SPOF), because a fault in that part escalates to cause the failure of the whole system.
	2. To make this process fault-tolerant, we would need to ensure that another machine can take over this task without missing any posts that should have been delivered,

10. **Blaming people for mistakes is counterproductive.** 
	- What we call “human error” is not really the cause of an incident, but rather a symptom of a problem with the socio-technical system in which people are trying their best to do their jobs. 
	- Often complex systems have emergent behavior, in which unexpected interactions between components may also lead to failures

11. Organizations are adopting a culture of **blameless postmortems**.
	- After an incident, the people involved are encouraged to share full details about what happened, without fear of punishment, since this allows others in the organization to learn how to prevent similar problems in the future.

12. **The shared-nothing architecture** (aka horizontal scaling or scaling out) involves a distributed system with multiple nodes, each of which has its own CPUs, RAM, and disks. 
	- Any coordination between nodes is done at the software level, via a conventional network.

13. It is widely recognized that the majority of the cost of software is not in its initial development but in its ongoing maintenance—fixing bugs, keeping its systems operational, investigating failures, adapting it to new platforms, modifying it for new use cases, repaying technical debt, and adding new features.

14. Every system we create today will one day become a **legacy system** if it is valuable enough to survive for a long time. To minimize the pain for future generations who need to maintain our software, we should design it with maintenance in mind.
